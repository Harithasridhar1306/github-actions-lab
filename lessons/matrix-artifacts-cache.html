Matrix, Artifacts & Cache

Three features that solve three different problems: more executions, moving files, and reusing dependency state.

Mental model

matrix = combinations · artifact = files · cache = reusable state

Learn the execution model first. Syntax comes second.

Today's build

Create a test matrix, pass a build artifact between jobs, then understand why a cache hit does not replace your install step.

01 · Understand

Don't confuse these features

matrix → fan out jobs artifact → move files between jobs cache → reuse dependency data

They solve different problems. A cache is not a deployment artifact, and a matrix is not a dependency mechanism.

02 · Build it

Turn one test into combinations

strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [20, 22]
runs-on: ${{ matrix.os }}

Two OS values × two Node values = four executions. Add another dimension and the combinations multiply.

03 · Pass a file

Artifacts bridge runner boundaries

- run: mkdir dist && echo release > dist/app.txt
- uses: actions/upload-artifact@v4
  with:
    name: app
    path: dist/

A later job can download the artifact. This is important because jobs may run on different runners.

04 · Add caching

A cache hit is not magic

- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm
- run: npm ci

Cache restores reusable dependency data. Your workflow still needs the appropriate install/build logic.

05 · Break it

Matrix failures can be selective

If one OS/version combination fails while the others pass, inspect the matrix values in the failed job. Don't treat the whole matrix as one environment.

Final challenge

Don't look it up yet. Explain what you would inspect and why.
