Reusable Workflows

Turn repeated CI/CD YAML into a stable interface with inputs, secrets and outputs.

Mental model

caller → reusable workflow → contract → implementation

Learn the execution model first. Syntax comes second.

Today's build

Create a reusable deployment workflow and call it from another workflow without copy-pasting deployment logic.

01 · Understand

A reusable workflow is an API

repo A ─┐ repo B ─┼→ shared deploy workflow repo C ─┘

The caller expresses intent. The reusable workflow owns implementation. Inputs, secrets and outputs become the interface.

02 · Define it

Use workflow_call

on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying ${{ inputs.environment }}"
03 · Call it

Keep callers small

jobs:
  deploy:
    uses: ./.github/workflows/deploy.yml
    with:
      environment: production

The caller does not need to duplicate the deployment steps.

04 · Break it

Breaking the interface

Rename an input in the reusable workflow and leave callers unchanged. The implementation may still be valid, but the contract has changed.

Think of reusable workflows as APIs: input names, required fields, secrets and outputs need compatibility thinking.
05 · Fix it

Centralisation creates blast radius

A shared workflow can remove huge amounts of duplication, but a bad change can affect many repositories. Validate the shared workflow and introduce changes deliberately.
