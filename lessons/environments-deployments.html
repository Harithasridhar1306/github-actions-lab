Environments & Deployments

Separate CI success from release control using environments, protection rules and deployment gates.

Mental model

build → deploy target → protection gate → release

Learn the execution model first. Syntax comes second.

Today's build

Deploy automatically to staging, then require an environment gate before production.

01 · Understand

Production can intentionally wait

build ↓ staging ↓ production environment ↓ approval / protection ↓ production steps

A waiting deployment is not necessarily a broken runner. Environment protection can deliberately pause a job.

02 · Build it

Target an environment

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
    steps:
      - run: echo "Deploying production"

Configure protection rules for the environment in repository settings.

03 · See it

Green job, waiting deployment

Build commands can all be green while the deployment job waits for approval. Read the job state carefully: queued, waiting, skipped and failed mean different things.

04 · Break it

The job never reaches the shell

If production is waiting, adding more echo commands will not help. Inspect the environment and its protection rules first.

Debug the state before debugging the command.
05 · Design it

Delivery and release are different concerns

CI can prove an artifact is buildable. Environment controls can decide when that artifact is released. Keeping those concerns separate makes deployment pipelines easier to reason about.

Final challenge

A production job is green but waiting. What should you inspect?

Don't look it up yet. Explain what you would inspect and why.

Reveal the answer
The targeted environment and its protection/approval state. The job may be waiting exactly as configured.
