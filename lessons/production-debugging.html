15 min · LESSON

Production Debugging

Diagnose Actions failures like an engineer: classify the symptom, form a hypothesis, gather evidence, then change one thing.

Mental model

symptom → hypothesis → evidence → smallest change → rerun

Learn the execution model first. Syntax comes second.

Today's build

Work through trigger, skip, runner, permission and dependency failures without YAML whack-a-mole.

01 · Classify first

What state are you actually seeing?

didn't trigger? queued? skipped? failed? cancelled? succeeded but wrong?

These states point to different layers. A skipped job and a failed shell command are not the same problem.

02 · Scenario

Works locally, fails in Actions

echo "OS=$RUNNER_OS"
echo "shell=$SHELL"
pwd
which terraform || true
terraform version || true

Compare the runner's OS, shell, PATH, tools, files and permissions with your local assumptions.

03 · Scenario

The deploy job is skipped

deploy:
  needs: [build, test]
  if: ${{ success() }}

Trace upstream. Did build or test fail? Was a job skipped? Did an if condition evaluate false?

04 · Scenario

Permission denied

Inspect the workflow's permissions and the identity being used. Avoid immediately replacing a scoped mechanism with a broader credential.

Make the smallest permission change that tests your hypothesis.
05 · Fix it

Use the hypothesis loop

1. State symptom 2. One hypothesis 3. One piece of evidence 4. One change 5. Rerun 6. Explain root cause

If you change five things at once, you may fix the workflow without learning why it failed.

Final challenge

A script works locally but fails on a GitHub-hosted runner. What do you compare first?

Don't look it up yet. Explain what you would inspect and why.

Reveal the answer
OS, shell, PATH, working directory, permissions and installed tools. The runner is part of the execution environment.
