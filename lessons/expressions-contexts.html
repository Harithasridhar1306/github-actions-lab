Expressions & Contexts

Learn where GitHub Actions values actually live and how to debug conditions that look right but behave wrong.

Mental model

context → expression → decision

Learn the execution model first. Syntax comes second.

Today's build

Inspect github context values, create a step output, then debug a condition using the wrong value.

01 · Understand

Contexts are structured data

Examples include github, steps, needs, inputs, vars and secrets. The key debugging question is: where does this value live?

if: ${{ github.ref == 'refs/heads/main' }}
02 · See it

Print the execution context

- run: |
    echo "ref=$GITHUB_REF"
    echo "sha=$GITHUB_SHA"
    echo "event=$GITHUB_EVENT_NAME"

Compare push and pull-request runs. The context changes with the event.

03 · Build it

Create a step output

- id: version
  run: echo "value=1.4.2" >> "$GITHUB_OUTPUT"
- run: echo "Version is ${{ steps.version.outputs.value }}"

The step needs an id so it can be addressed through the steps context.

04 · Break it

A valid expression can still be wrong

if: ${{ github.ref == 'main' }}

For a normal push, the ref is shaped like refs/heads/main. The expression is valid YAML and valid Actions syntax, but the comparison is wrong.

Print the value you are comparing before changing the condition.
05 · Fix it

Think in exact values

Ask: what context? what lifecycle moment? exact value? exact type? This is faster than guessing between github, steps, needs and env.

Final challenge

Which expression checks a push to main?

Don't look it up yet. Explain what you would inspect and why.

Reveal the answer
github.ref == 'refs/heads/main'. The important part is using the github context and comparing the actual ref shape.
